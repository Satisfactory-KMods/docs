You can add new resources, miners and other KAPI DataAssets without linking
directly against [KAPI](/satisfactory-plus/kapi/). Ship YAML packs in a
**`DataForge/` folder** inside your mod. [KDataForge](/kdataforge/) resolves KAPI
at runtime through Unreal reflection and also works when KAPI is absent.

:::note
This pattern works for any mod, including Satisfactory Plus. SF+ does not
currently ship its own `DataForge/` folder. The example below comes from
[KDataForge's reference sample pack](/kdataforge/getting-started/) and uses real
KAPI DataAsset classes.
:::

## Why this is a _soft_ dependency

Unlike KAPI itself, KDataForge does **not** link against KAPI at build time:

- `KDataForge.uplugin`'s `Plugins` array lists only `SML`, with no `KAPI` entry.
- None of KDataForge's four module `.Build.cs` files reference `KAPI` in `PublicDependencyModuleNames`.
- Instead, `KDFSubsystem.cpp` resolves KAPI's subsystem **by string path through Unreal reflection**, only if it's actually present:

```cpp
// KAPI is optional resolve and invoke via reflection so no link dependency exists.
if (UClass* KAPIClass = FindObject<UClass>(nullptr, TEXT("/Script/KAPI.KAPIDataAssetSubsystem")))
{
    if (UGameInstanceSubsystem* KAPISubsystem = GameInstance->GetSubsystemBase(KAPIClass))
    {
        if (UFunction* ScanFunction = KAPISubsystem->FindFunction(FName(TEXT("StartScanForDataAssets"))))
        {
            KAPISubsystem->ProcessEvent(ScanFunction, nullptr);
        }
    }
}
```

This code compiles and loads when KAPI is absent. The class lookup returns null,
and execution skips the block. KDataForge therefore remains a soft dependency
instead of an optional-at-compile-time hard dependency.
