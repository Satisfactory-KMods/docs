Write `properties:` as a mapping from property paths to values. A plain value performs `set`,
replacing the current value. Add `$op` inside a property's value to choose another operation and
pass its arguments:

```yaml
properties:
  mDisplayNameOverride: true
  mManufactoringDuration:
    $op: multiply
    value: 0.5
  mIngredients:
    $op: append
    value:
      ItemClass: /Game/Example/Desc_Item.Desc_Item_C
      Amount: 4
```

The mapping form also works in generated content and instanced-object `properties:` blocks. A
nested struct mapping is a plain `set` value unless it contains `$op` directly. Use the ordered
`path`/`value` list when one property needs several operations, because YAML mapping keys cannot
repeat. Both forms use the same operations and argument names; see
[YAML Schema](/kdataforge/reference/yaml-schema#property-paths).
For a condition on one operation, use a conditional patch entry or the legacy list form;
`conditions:` is not a field inside a mapped `$op` value.

The 25 operations are grouped by the kind of
property they act on: numeric math and clamping, container mutation for arrays, sets, maps, and
tag containers, string concatenation, array reordering and deduplication, and cross-property copy
or move.

See [Patching (type: cdo)](/kdataforge/features/patching-cdo) for the full patch
structure these entries live inside. See [Property Types](/kdataforge/features/property-types)
for what each underlying property looks like in YAML.

## Select every gameplay tag container

Use the quoted operation path `'@tagContainers'` to apply the same operation to every
top-level `FGameplayTagContainer` on each target. Inherited fields are included. With
`applyToSubclasses: true`, KDF selects fields again for each subclass, including
additional fields on classes loaded later. An object without matching fields is a no-op.

```yaml
type: cdo
patches:
  - target: /Script/FactoryGame.FGResourceDescriptor
    applyToSubclasses: true
    properties:
      '@tagContainers':
        $op: append
        value:
          - KMods.PlannerResource
```

Register tags before using them, for example through a `type: gametag` document.
Supported operations are `set` (also the default), `append`, `prepend`, `remove` and
`clear`. Tag containers are sets: adding an existing tag does not create duplicates.
Each selected field gets its own normal snapshot and patch record for rollback.
Use consecutive `remove` and `append` entries in the ordered list form to replace one set of tags
with another.

The selector does not recurse into nested structs, objects or arrays and cannot be
combined with a suffix such as `.Child` or `[0]`. It is only an operation destination,
not a concrete property path for `where`, `from`, templates or single-property
read/edit APIs. Use an actual field name in those contexts. Keep quotes: YAML does
not allow an unquoted scalar starting with `@`.

## append_unique: array

Appends each incoming value only if no equal element is already present. Existing duplicates and
their order stay unchanged; repeated incoming values are added at most once. This matches a
MergeUnique-style update without deduplicating the destination array:

```yaml
mAllowedResourceForms:
  $op: append_unique
  value:
    - RF_GAS
```

For example, an array with two `RF_LIQUID` entries gains one `RF_GAS` entry. Applying the same
operation again leaves it unchanged. `value` accepts one element or a sequence; an empty sequence
is a successful no-op. Equality uses the reflected element type, including enum, struct and object
identity. Arrays only: use ordinary `append` for sets/maps. Subobject definitions with `class` and `properties`
creation is rejected; reference an existing object or use `append` to create a new instance.
Malformed operands fail without leaving a partial array edit.

## update_where: array of structs

`update_where` checks every struct element in an array and partially updates every match. The
`where` path is relative to one element, not the patched object. `value` must be a struct mapping;
members omitted from that mapping keep their current values:

```yaml
mProduct:
  $op: update_where
  where:
    path: ItemClass
    equals: /OldMod/Items/Desc_Old.Desc_Old_C
  value:
    ItemClass: /NewMod/Items/Desc_New.Desc_New_C
```

Use a sequence under `where` for several clauses. They use `AND` by default. Set sibling
`whereMode: OR` to update an element when any clause matches:

```yaml
mProduct:
  $op: update_where
  whereMode: OR
  where:
    - path: ItemClass
      equals: Desc_OldA_C
    - path: ItemClass
      equals: Desc_OldB_C
  value:
    ItemClass: Desc_New_C
```

`whereMode` accepts `AND` or `OR` case-insensitively and requires `where`. Clauses accept the same
operators as target filters: `equals`, `notEquals`, numeric comparisons, `contains`, `notContains`,
`in`, `notIn`, `matches`, and `isEmpty`. Nested paths and `[*]` reads are supported inside the
element.

Every matching element is updated. No match is an error, protecting patches against upstream array
changes. Invalid predicates or values roll back the whole array operation; partial writes are not
kept. Only arrays whose elements are reflected structs are supported. This operation is useful for
recipe `mIngredients` and `mProduct` arrays because it does not depend on element order.

## replace_refs: reflected reference trees

`replace_refs` searches below one property and replaces every exact matching object or class
reference. It follows reflected structs, arrays, sets, maps, and instanced objects. This makes the
same operation usable for recipe inputs/outputs and for nested schematic unlock or dependency
objects without knowing array indexes or concrete unlock subclasses:

```yaml
mUnlocks:
  $op: replace_refs
  from: /OldMod/Recipes/Recipe_Old.Recipe_Old_C
  value: /NewMod/Recipes/Recipe_New.Recipe_New_C
```

Use `mIngredients:` or `mProduct:` as the mapping key for recipes, `mUnlocks:` for unlock payloads,
`mSchematicDependencies:` for schematic dependencies, or `mTaskDependencies:` for KAPI
delivery-task dependencies. The selected property is also the traversal boundary: unrelated
properties on the target are never searched.

Both hard and soft object/class references are supported. Instanced objects are traversed, but KDF
does not follow ordinary external object references into unrelated assets. `from` and `value` must
be scalar references. The replacement must satisfy every matched property's reflected class type.
Zero matches, incompatible targets, or excessive nesting fail the operation. All matched references
are validated before writing; a failure keeps original values.

## set (default): everything

`set` overwrites the property outright. It works on any property type, which is why it can be
left implicit. On `mDisplayName` (an `FString`), setting a value replaces the string:

```yaml
mDisplayName: 'Reinforced Iron Ingot' # set is implied
```

### Bitmask operations

`set` accepts one flag name or a sequence of flag names. KDataForge resolves and ORs names from the
property's `BitmaskEnum`. Raw numeric masks are accepted by `set` only. Plain integer bitmask
handling requires `WITH_METADATA`, retained property metadata, and an already-loaded enum; missing
metadata or an unresolved enum leaves ordinary integer conversion. See
[Property Types](/kdataforge/features/property-types#bitmask-integer-properties-with-bitmaskenum-metadata)
for named mask/index forms, width limits, and Shipping-build limitations.

For one flag:

```yaml
mParentTask: Above
```

For several flags:

```yaml
mParentTask:
  - Above
  - Left
```

## add / subtract: numeric

`add` and `subtract` do in-place arithmetic on a plain numeric property. They add or subtract
`value` from whatever is currently stored. Both reject enum-backed integers (see the callout
below), since there is no meaningful "current + 1" for an enum ordinal:

```yaml
mTechTier:
  $op: add
  value: 1
mTimeToComplete:
  $op: subtract
  value: 30
```

## multiply / divide: numeric

`multiply` and `divide` scale a numeric property by `value`. Setting `mManufactoringDuration` to a
fraction of itself halves the crafting time, while dividing `mEnergyValue` doubles the effective
fuel efficiency. Dividing by `0` is rejected outright, rather than producing infinity or NaN:

```yaml
mManufactoringDuration:
  $op: multiply
  value: 0.5
mEnergyValue:
  $op: divide
  value: 2
```

## min / max: numeric (result = min/max of current and value)

`min` enforces a ceiling: the property is replaced with whichever is smaller, the current value or
`value`. `max` enforces a floor, replacing the property with whichever is larger. Neither can push
the property past `value` in the opposite direction, which makes them useful for "never exceed" or
"never fall below" balancing passes across many objects at once:

To cap sink points at 100:

```yaml
mResourceSinkPoints:
  $op: min
  value: 100
```

To raise them to at least 50:

```yaml
mResourceSinkPoints:
  $op: max
  value: 50
```

To enforce both bounds in one mapping entry, use `clamp` with `min: 50` and `max: 100`.

:::caution
**Enum-backed properties don't count as numeric.** `mStackSize` on `FGItemDescriptor` is an
`EStackSize` **enum** (`SS_ONE`…`SS_HUGE`/`SS_FLUID`), not a plain int `min`/`max`/`clamp`/
`add`/`subtract`/`multiply`/`divide` are all rejected on it (`op not supported`); only `set` with
an enum value name works. See
[Property Types → Enums](/kdataforge/features/property-types#enum-typed-enum-class-and-tenumasbyte).
:::

## clamp: numeric

`clamp` is the two-sided version of min/max: instead of a single `value`, it takes `min` and `max`
keys and pins the current value inside that range in one step:

```yaml
mMenuPriority:
  $op: clamp
  min: 0
  max: 999
```

## append: array / set / map / string / tag container / bitmask

`append` adds to the end of a container, or concatenates onto a string. It behaves differently
depending on the target property's kind.

For arrays and sets, `value` can be a single item or a sequence to add several items at once. For
strings, it concatenates text. For tag containers, it adds tags. For maps, `value` must be a map,
and KDataForge merges those key/value pairs into the existing map:

```yaml
# array: adds element(s) at the end
mIngredients:
  $op: append
  value:
    ItemClass: /Game/FactoryGame/Resource/RawResources/Coal/Desc_Coal.Desc_Coal_C
    Amount: 1
# string: concatenates
mDisplayName:
  $op: append
  value: ' (rebalanced)'
# tag container: adds tags
mGameplayTags:
  $op: append
  value:
    - MyPack.Rebalanced
# map: merges entries
mSomeMap:
  $op: append
  value:
    Iron: 10
# bitmask: OR-adds flags
mParentTask:
  $op: append
  value:
    - Above
    - Left
```

For bitmasks, `append` ORs named flags into current mask. It does not accept raw integer masks.
For instanced `UObject` arrays, an appended value can be a map with `class` and nested `properties`; KDataForge
constructs the new subobject before inserting it into the array:

```yaml
mUnlocks:
  $op: append
  value:
    class: /Game/FactoryGame/Unlocks/BP_UnlockRecipe.BP_UnlockRecipe_C
    properties:
      mRecipes:
        - Recipe_MyGeneratedRecipe
```

:::note
String operations on `FText` properties (like `mDisplayName` when it is a localized text field)
produce plain culture-invariant text the original localization key/namespace is dropped, so an
`append`/`prepend`/`clear` on a translated string stops it from tracking further translation
updates. See [Localization](/kdataforge/features/localization) if you need the
result to stay localizable instead.
:::

## prepend: array / set / string (tag containers and bitmasks: same as append)

`prepend` mirrors `append`, but it adds at the front instead of the end for arrays, and inserts
before the existing text for strings. Tag containers treat it identically to `append`, since a tag
container has no ordering. Sets also treat it like `append`, because sets have no ordering.
Bitmasks also treat it like `append` and OR-add named flags. Maps do not support `prepend` at all:
only `append` merges into a map.

```yaml
mDisplayName:
  $op: prepend
  value: '[MP] '
```

## insert: array

`insert` places one or more elements at a specific `index` inside an array, rather than always at
the end, and shifts later elements back. An out-of-range index fails with an error, instead of
clamping to the array's bounds. Instanced `UObject` array entries may use the same `{ class,
properties }` map accepted by `set`, `append`, and `prepend`:

```yaml
mIngredients:
  $op: insert
  index: 1
  value:
    ItemClass: /Game/FactoryGame/Resource/RawResources/OreCopper/Desc_OreCopper.Desc_OreCopper_C
    Amount: 1
```

## remove: array (by value) / set (by value) / map (by key) / tag container / bitmask

`remove` deletes by content rather than by position. On arrays and sets, it deletes every element
that matches `value` exactly. An array remove that matches nothing fails, rather than silently
doing nothing. On maps, `value` is the _key_ to delete, and on tag containers, `value` is the tag
(or list of tags) to remove. On bitmasks, it clears every named bit with AND-NOT:

```yaml
# removes every element equal to the value
mIngredients:
  $op: remove
  value:
    ItemClass: /Game/FactoryGame/Resource/RawResources/OreIron/Desc_OreIron.Desc_OreIron_C
    Amount: 1
# map: value is the key
mSomeMap:
  $op: remove
  value: Iron
mGameplayTags:
  $op: remove
  value: KMods.WikiExclude
# bitmask: clears named bits
mParentTask:
  $op: remove
  value: Left
```

## remove_at: array

`remove_at` deletes the element at a specific position instead of matching by value. It is the
right tool when you know the slot but not, or don't want to spell out, the exact contents:

```yaml
mProduct:
  $op: remove_at
  index: 1
```

## clear: array / set / map / string / tag container / bitmask

`clear` empties a container-shaped property entirely: arrays, sets, maps, and tag containers all
lose every element. Strings are reset to empty, rather than to their class-default text. On a
metadata-recognized bitmask, `clear` writes `0`:

```yaml
mSubCategories:
  $op: clear
# bitmask: sets mask to 0
mParentTask:
  $op: clear
```

## swap: array

`swap` exchanges the elements at two positions, `index` and `with`, in an array without touching
anything else in the list. It is useful for reordering a couple of entries without rewriting the
whole array:

```yaml
mIngredients:
  $op: swap
  index: 0
  with: 1
```

## replace: array

`replace` overwrites the element at `index` with a new `value`, keeping every other element and
the array's length unchanged:

```yaml
mProduct:
  $op: replace
  index: 0
  value:
    ItemClass: /Game/FactoryGame/Resource/Parts/SteelIngot/Desc_SteelIngot.Desc_SteelIngot_C
    Amount: 2
```

## duplicate: array (copies element to the end)

`duplicate` copies the element at `index` and appends the copy to the end of the same array. It is
handy for cloning an existing ingredient or product entry as a starting point, before tweaking it
with a follow-up `replace`:

```yaml
mProduct:
  $op: duplicate
  index: 0
```

## sort / reverse: array

`sort` reorders an array in ascending order. Numeric and string inner types sort by their actual
value. Anything else, such as structs or object references, sorts by its exported text form.
`reverse` flips the current order of every element:

```yaml
# numeric/string inner types sort by value; others by text form
mRelevantEvents:
  $op: sort
mSubCategories:
  $op: reverse
```

## unique: array (removes later duplicates; sets: no-op)

`unique` walks an array and removes any element that is byte-identical to an earlier one, keeping
the first occurrence of each value. Running it on a set is always a no-op, since a set is already
guaranteed to contain no duplicates:

```yaml
mSubCategories:
  $op: unique
```

## copy: any property (from another path on the same object)

`copy` reads the value at another property path (`from`) on the same object and writes it into the
target property. When source and destination are exactly the same property type, it copies the raw
value directly. Otherwise, it round-trips through each property's text representation.

This means copying between compatible but different types, for example a plain string into a name,
can still work, as long as the text parses back cleanly for the destination type:

```yaml
mAbbreviatedDisplayName:
  $op: copy
  from: mDisplayName
```

## move: copy, then reset the source to its default

`move` performs the exact same copy as `copy`, then clears the source property back
to its default value. This makes it the right choice when a value should live at the new path
_instead of_ the old one, rather than in both places:

```yaml
mDescription:
  $op: move
  from: mScannerDisplayText
```
