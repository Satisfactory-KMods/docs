KDataForgeJS is the TypeScript adapter for KDataForge. It uses KDataForge's catalog, validation,
transactions, lifecycle, and limits rather than exposing Unreal objects directly. The current dev
build is intended for testing and API feedback.

Install KDataForgeJS alongside KDataForge. A scripted pack still uses a normal `DataForge` root and
`pack.yml`, but its entry point is always `scripts/main.ts`:

```text
DataForge/
├── pack.yml
└── scripts/
    ├── main.ts
    └── lib.ts
```

## Write the entry point

Import `defineHandler` and `defineMeta` from the built-in module. `defineHandler` gives `ctx` its
complete generated type, so do not write a separate context interface.

```ts
import { defineHandler, defineMeta } from "@sf-kmods/kdataforgejs";

export const meta = defineMeta({ id: "example.typed-pack", version: 1 });

export default defineHandler(async (ctx) => {
    console.info("loaded", ctx.catalog().digest);
    await Promise.resolve();
});
```

Local static imports such as `./lib` are supported when they remain inside the pack's prepared
source graph. KDataForgeJS does not read `package.json` or `node_modules`, resolve external packages,
or allow dynamic `import()`.

## Use generated types

KDataForge generates TypeScript declarations from the sealed catalog. The virtual `satisfactory`
module exposes authorized UE classes, properties, structs, and functions as normal TypeScript symbols.
Catalog IDs stay internal runtime ABI details rather than pack-author API.
Open the pack in KDataForge Editor, CodeOSS, or VS Code to get the same completion and diagnostics.
Do not replace generated declarations with hand-written copies.

KDataForge Editor writes the pack-specific result to
`DataForge/typescript/kdataforgejs/kdataforge.generated.d.ts`. That file contains both core-module
augmentations and `declare module "satisfactory"`, and its header records the sealed catalog digest.
Runtime and declarations therefore consume one reflection snapshot.

The repository's `KDataForgeJS/Examples/TypedStarter` folder is a complete project that can be opened
directly. It includes `main.ts`, `lib.ts`, media and YAML imports, generated declarations, and a
strict `tsconfig.json`; it requires no package installation.

## Use UE-native generated APIs

Import generated UE symbols, resolve a typed class, then use CDO properties and functions directly:

```ts
import { FGItemDescriptor } from "satisfactory";

const itemClass: Class<FGItemDescriptor> = ctx.getClass("/Script/FactoryGame.FGItemDescriptor");
const cdo = itemClass.getClassDefaultObject();

console.info(cdo.mDisplayName.get());
console.info(FGItemDescriptor.GetItemName(itemClass));
```

Writable UPROPERTY proxies also expose `set(value)`. Reflected USTRUCT arrays contain typed,
revision-checked struct views. A TypeScript type or path written by the pack cannot grant a capability
that the catalog did not seal.

Native functions are explicit allowlists, not automatic exposure of every `BlueprintPure` function.
A trusted reflection contributor can expose static native, `BlueprintPure`, read-only functions from a
`UBlueprintFunctionLibrary`; KDataForgeJS then generates their signatures and runtime wrappers. Plain C++
virtual functions without `UFUNCTION` cannot be reflected or intercepted through this API and still need
a typed native hook integration.

### Import pack files

`ctx.import(kind, path)` reads only files declared by the pack and included in its verified source
manifest. Supported kinds are `text`, `yaml`, `binary`, `image`, and `audio`.

```ts
const settings = ctx.import("yaml", "settings.yml");
const sound = ctx.import("audio", "alert.ogg");
```

Paths are pack-relative. KDataForge validates the normalized path, kind, digest, and size before the
runtime receives the value. URLs and absolute paths are rejected.

### Work with CDOs and object handles

Objects, actors, and nested struct values use opaque handles. They are not C++ pointers or UObject
addresses. KDataForge checks world, realm, catalog, generation, type, authority, lifecycle, and
access again for every operation.

The `itemClass` and `cdo` values above are opaque handles. `getClassDefaultObject()` resolves the CDO
through that class handle; `mDisplayName.get()` performs a checked property read.

The class must be allowed by the pack's reflection catalog. Do not serialize handles or retain them
across reload, world travel, realm replacement, or catalog regeneration; resolve new handles after
those transitions.

## Events, hooks, ticks, and timers

Events and hooks are catalog-generated and typed. Use generated keys rather than copying raw catalog
IDs into pack code. Keep returned subscriptions so you can clean them up explicitly; realm shutdown
also removes remaining registrations.

```ts
const event = ctx.onTyped("provider.event", "example.event", (value) => {
    console.info("event", value);
});

const tick = ctx.registerTick(
    "example.inventory-sorter",
    (deltaSeconds) => console.debug("sort", deltaSeconds),
    { every: 5, requireGameThread: true },
);

event.unsubscribe();
tick.unsubscribe();
ctx.unregisterTick("example.inventory-sorter");
```

Use `ctx.hook(target, eventId, phase, callback)` for authorized `before`, `after`, or `replace`
hooks. Use `ctx.setTimeout(callback, seconds)` for a bounded one-shot timer. Every callback remains
subject to realm deadlines, quotas, authority, and lifecycle validation.

## Create content and classes

Scripted packs can use the same KDataForge handlers as YAML through `ctx.applyDocument`. Typed
helpers also cover items, recipes, actors, behaviors, and dynamic classes. Document application and
class definition run during `Initialization`; gameplay work belongs in the runtime phase and should
be guarded with `ctx.isAuthority()` when only the authority may perform it.

KDataForge validates the complete change before commit and compensates prepared mutations if a later
step fails. There is no separate `save()` call and no direct write to cooked Unreal packages.

## Runtime boundaries

The dev build includes the native ECMAScript built-ins supplied by its pinned QuickJS-NG runtime,
including promises, collections, typed arrays, iterators, `Math`, `Number`, `BigInt`, `JSON`, and
`console.log`/`info`/`warn`/`error`/`debug`.

It intentionally does not expose Node.js, npm packages, browser DOM APIs, sockets, web servers,
remote downloads, or unrestricted filesystem access. `Intl`, `Temporal`, WebAssembly, and
`Atomics.waitAsync` are also absent from the pinned runtime. Networking and external packages are
post-release work and require separate authority and security contracts.

When reporting a dev-build problem, include the pack ID, script path, relevant log line, generated
catalog version, and minimal reproduction.
