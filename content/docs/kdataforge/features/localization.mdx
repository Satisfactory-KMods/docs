KDataForge supports both the standard Unreal `.po` / `.locres` workflow for keyed YAML text and
runtime translation documents (`type: localization`).

## Compile YAML texts with Unreal localization

Use this workflow when a mod already has a Localization Target and you want YAML-authored names,
descriptions, or other keyed `FText` values included in its normal translation pipeline:

```yaml
type: cdo
conditions:
  hasMod: [SatisfactoryPlus, KLib]
patches:
  - target: /KLib/Assets/Buildings/PressureRegulatorValve/Build_PressureRegulatorValve.Build_PressureRegulatorValve_C
    properties:
      - path: mDisplayName
        value:
          key: 895CFBF74588721183546EBD628AA06D
          ns: ST_Klib
          source: Pressure Trigger Valve
```

The gather integration preserves `ns`, `key`, and the decoded `source` string, including line breaks,
quotes, backslashes, Unicode, `{VarName}` placeholders, and literal percent characters. Keep these
fields literal; the gather does not evaluate templates or execute runtime patches. A plain scalar
`value: Pressure Trigger Valve` has no stable localization key and is not gathered by this integration.
An omitted `ns` uses an empty namespace, matching the runtime text conversion.

Pack display metadata supports the same text form. Keep stable keys when changing wording:

```yaml
ref: ExamplePack
name:
  ns: ExamplePack
  key: Pack.Name
  source: Example Pack
description:
  ns: ExamplePack
  key: Pack.Description
  source: Production adjustments for this mod.
version: 1.0.0
```

Scalar names/descriptions remain compatible, but explicit keyed maps are required when those
labels need compiled translations. The pack `ref` and dependency references are technical IDs.

### Required target settings

1. Enable **KDataForge** and build its editor modules. Restart the editor after updating the plugin
   so **KDataForgeLocalization** is loaded. This editor module supports commandlets and is not
   needed in the packaged game.
2. Keep the mod's normal Localization Target, native language, translated languages, manifest and
   archive names.
3. Add `CommandletClass=GatherKDataForgeText` as a gather configuration step **before**
   `GenerateGatherManifest`. Keep existing source and asset steps for texts authored in C++ or
   Unreal assets. YAML gathering needs no `h` file filter, generated headers, or extra search path.
4. Run the target's checked-in gather configuration with `UnrealEditor-Cmd -run=GatherText`, then
   export PO files, translate/import them, and compile `.locres`. Existing Dashboard export/import/
   compile actions and Tolgee workflows can use these same catalogs. Do not enable placeholder
   conversion. If Dashboard settings regenerate the gather configuration, retain or restore the
   dedicated KDF step before gathering again.
5. Package and load the mod's Localization Target as usual. The resulting `.locres` translates the
   keyed `FText` that KDataForge creates at runtime.

The target name must match either the plugin name or a target declared in that plugin's
`.uplugin` `LocalizationTargets`. Each matching target gathers the plugin's own pack texts. The
YAML's namespace does **not** select its owning mod or target: in the example, a file shipped inside
SatisfactoryPlus is gathered into the **SatisfactoryPlus** target even though its namespace is
`ST_Klib` and its patch changes a KLib class. Use manifest dependencies if several targets share texts
and you want Unreal to exclude already gathered entries.

The integration discovers `DataForge`, legacy `data-editor`, and directories containing `pack.yml`
under the owning plugin, and reads their `.yml` and `.yaml` files recursively, including nested packs,
multi-document streams, and keyed text in `pack.yml`. Initial root discovery uses a recursion limit
of six and skips engine/build directories such as `Content`, `Source`, `Config`,
`Intermediate`, and `Saved`. Dot-prefixed directories, `Docs`, and `Scripts` are also excluded,
both during root discovery and when collecting documents inside a root. Pack `enabled` flags, mod
conditions, and runtime dependencies do not
filter localization gathering: optional compatibility content needs translations even when its
target mod is absent in the editor. YAML outside that plugin is not included.

The KDF step adds each decoded native text directly to Unreal's gather manifest. Source references
are stable, plugin-relative YAML locations such as `DataForge/buildings/valve.cdo.yml:14`, with the
line pointing to the `source` value. No temporary headers or operating-system user paths enter
manifest or PO references. Namespace, key, and decoded source text remain unchanged.
Preview gathers include YAML when gathering **Source** or **All**, matching Unreal's source-text
collector; **Asset** previews do not collect YAML.

### Commandlet configuration

Retain the normal manifest/archive/language settings. Add the dedicated KDF step before manifest
creation; renumber any subsequent steps to keep a unique, increasing sequence:

```ini
[GatherTextStep0]
CommandletClass=GatherKDataForgeText

[GatherTextStep1]
CommandletClass=GenerateGatherManifest

[GatherTextStep2]
CommandletClass=GenerateGatherArchive
```

This minimal example gathers only YAML. Keep existing `GatherTextFromSource` and
`GatherTextFromAssets` steps when the target also owns C++ or asset texts. The SF+ configuration
already includes all three collectors in the correct order.

```powershell
& 'C:/Program Files/Unreal Engine - CSS/Engine/Binaries/Win64/UnrealEditor-Cmd.exe' `
  'C:/Modding/FactoryGame.uproject' -run=GatherText `
  '-config=C:/Modding/Mods/GameFeatures/SatisfactoryPlus/Config/Localization/SatisfactoryPlus_Gather.ini' `
  -EnablePlugins=KDataForge -unattended
```

`ManifestName=SatisfactoryPlus.manifest` identifies the SatisfactoryPlus target. The KDF plugin
must be enabled in the commandlet process. Run normal export/import/compile steps afterward;
adding `.yml` as a C++ source file filter is not a replacement for `GatherKDataForgeText`.

### KMods CI/CD translation script

The KMods workspace script includes YAML text gathering in its normal translation flow:

```powershell
# Same local stages as CI; pull translations without uploading or deleting Tolgee keys
.\translation-scripts\sync_translation.ps1 -Plugins SatisfactoryPlus -SkipUpload

# Local gather/export check without contacting Tolgee
.\translation-scripts\sync_translation.ps1 -Plugins SatisfactoryPlus -LocalizationSteps "Gather,Export" -SkipTolgee
```

Build `FactoryEditor` and the `KDataForgeLocalization` editor module before running the script.
CI does this before translation sync. The gather command enables KDataForge explicitly and uses
an effective config at `exports/<Mod>/<Mod>_Gather.ini`. Keep the dedicated
`GatherKDataForgeText` step in each mod's checked-in gather configuration; the script preserves it.
Its legacy source-gather and `h`-filter setup remains harmless for ordinary C++ texts but does not
gather YAML by itself. Existing manifest identity, languages, dependencies, and asset gathering
stay intact. The script does not rewrite saved gather settings.

The script verifies the YAML bridge log and fails on missing bridge output, YAML errors, or failed
gather/export/import/compile commands. CI stops before packaging when translation sync fails.
Stage logs are under `exports/`, for example `exports/SatisfactoryPlus_gather.log`.

`-SkipUpload` skips only the Tolgee upload and cleanup. It still gathers, exports, pulls, imports,
and compiles by default. To reuse an existing manifest without gathering, request
`-LocalizationSteps "Import,Compile"` explicitly. CI does not upload newly gathered source keys;
run the normal sync without `-SkipUpload` separately to make those keys available in Tolgee.
After gathering/exporting, the current native English PO is retained when copying pulled
translations, so a Tolgee download cannot replace freshly gathered YAML source keys.
With `-SkipUpload`, only cloud translations matching the current exported source are imported.
Retired cloud keys are excluded; new or untranslated entries keep the native-language fallback.
Normal upload sync retains strict source-parity checks.

### Gather diagnostics

The log category **LogKDFLocalization** reports how many YAML files supplied text for each target.
An entry such as `Target 'SatisfactoryPlus': injected localization sources from 1 YAML file(s)`
confirms that the native YAML gather step ran. A second log entry reports the keyed text count.
Check the exported PO for your namespace/key and the actual relative YAML location before uploading
it for translation. There is no generated `.h` file to ship or edit.

Malformed/unreadable YAML and conflicting source strings for the same namespace/key produce
errors. Resolve these before importing or compiling translations. Conflicts with gathered asset or
C++ texts also use Unreal's normal conflict reporting. Empty source strings are not gathered.
If no gather log appears, check that the plugin/editor module is loaded, the configuration includes
`GatherKDataForgeText` before manifest generation, and the target name belongs to the mod. A source
gather step alone no longer creates temporary YAML headers. Targets without KDF pack roots retain
a zero-file receipt for compatibility with existing workspace pipeline checks.

Changing a source string can invalidate an older translation because Unreal checks the source
hash. Re-gather and translate the changed source. Avoid reusing another mod's namespace/key for
different text unless you deliberately intend to override that shared identity.

## Runtime translation documents

`type: localization` injects translations directly into the running localization manager without
compiling `.locres`. These translation documents are not gathered as native texts by the native gather
integration; use keyed `FText` maps in your content documents for the compiled workflow above.

The `Localization` stage runs after `GameTags`/`Assets` and before `CDOChanges`. Its entries key is
`entries`, a map from key to either a scalar or a block map with `source` and `text` fields.

## Simple key entries: new text

The scalar form registers a brand new localized text under `namespace:` and key. This works for
your own content's `FText` keys, or anyone else's, as long as the namespace and key match:

```yaml
# file: de.localization.yml
type: localization
namespace: MyPack
culture: de # prefix-matched: also applies for de-DE, de-AT, …
entries:
  MySuperIngot_Name: 'Superbarren'
  MySuperIngot_Desc: 'Ein weit überlegener Barren.'
```

## `source` + `text` map: overriding an EXISTING text

The map form overrides a text that **already exists** (vanilla or modded) by its original source
string:

```yaml
type: localization
namespace: MyPack
culture: de
entries:
  IronIngot_Renamed:
    source: 'Iron Ingot'
    text: 'Eisenbarren (überarbeitet)'
  SchematicOverride:
    source: 'Super Ingot Smelting'
    text: 'Superbarren-Verhüttung'
```

> ⚠️ **Source-hash matching.** UE identifies a localized text by its namespace/key plus a hash of
> the original source string. The `source:` you give must be **byte-identical** to the current
> original text: spacing, punctuation, and capitalisation all matter. If a game update changes
> the source string, the override silently stops matching. Copy the exact string from the game,
> don't retype it. Omitting `source:` uses `text:` as the source too, which only works for
> **new** keys. The scalar form above is the same thing written shorter.

## How it's applied

Localization entries are applied through the same mechanism the engine's own localization system
uses to load `.locres` files, so there is nothing KDataForge-specific for the game to special-case.

## Bidirectional prefix matching for `culture:`

```yaml
culture: de        # matches current language de, de-DE, de-AT, …
culture: pt-BR      # matches only pt-BR (a more specific prefix than pt)
# omit culture:     # entries apply for EVERY language
```

The match is **bidirectional prefix matching**: either the current language starts with `culture:`,
or `culture:` starts with the current language. `culture: de` applies when the running game is set
to `de-DE`, **and** `culture: de-DE` would also apply if the game were set to plain `de`. Whichever
side is the shorter prefix wins the comparison. In practice, prefer the shortest culture code that
covers your translation, `de` rather than `de-DE`, unless you specifically need a regional variant.

Documents whose `culture:` doesn't match the current language are skipped with an `Info`
diagnostic. This is not a warning: it's expected, not an error.

## Loading changes

Localization changes are loaded on the next session start.

A complete worked translation (item + schematic + German locale file, applied together) is part of
the end-to-end pack in [End-to-End Pack](/kdataforge/examples/end-to-end-pack).

## Troubleshooting

- **My override isn't taking effect.** This is almost always the source-hash mismatch described
  above. Copy the original string straight out of the game, or the base-game source if you have
  it, rather than retyping it from memory. A single missing period or extra space is enough to
  break the match silently.
- **Translation shows in one culture but not another.** Check for a stray `culture:` on the file.
  Omitting it entirely is usually what you want, unless you're intentionally splitting
  translations per locale across files.
- **New key works, but overriding an existing key doesn't.** New keys, using the scalar form,
  don't need `source:` to match anything since there's nothing to match yet. Overrides, using the
  map form, do need it. If you're not sure which one you need, ask yourself: does this text
  already exist in the game?
