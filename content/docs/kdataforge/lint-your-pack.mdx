The [KPatchwork repository](https://github.com/Satisfactory-KMods/KPatchwork) includes a static
[KDataForge pack linter](https://github.com/Satisfactory-KMods/KPatchwork/blob/main/Lint/lint_packs.py).
Run it after writing or changing a pack to catch malformed YAML and common schema mistakes without
starting Satisfactory.

The linter is also the validation step used by KPatchwork's pull-request CI. It reports every issue
it finds in one run: warnings are printed but do not fail the command, while errors produce exit
code `1`.

## Get the linter

Install [uv](https://docs.astral.sh/uv/getting-started/installation/) and Git, then clone
KPatchwork:

```bash
git clone https://github.com/Satisfactory-KMods/KPatchwork.git
cd KPatchwork
```

KPatchwork currently requires Python 3.11 or newer. `uv run --locked` creates the required Python
environment from the repository's lockfile, so you do not need to install PyYAML manually.

## Choose the correct root

The `--root` argument is the directory the linter searches recursively for `pack.yml` files and
YAML documents. It expects every manifest to be at least one directory below that root.

For the standard standalone layout from [Getting Started](/kdataforge/getting-started),
pass `<your-mod>`, not its `DataForge` child:

```text
<your-mod>/
  DataForge/
    pack.yml
    faster-smelting.cdo.yml
```

From the cloned KPatchwork directory, replace the placeholder with the absolute path to your mod:

```bash
uv run --locked Lint/lint_packs.py --root "<your-mod>"
```

For a repository containing several nested packs, pass their common container instead:

| Pack layout                                       | `--root` value         |
| --------------------------------------------------- | ------------------------- |
| `<your-mod>/DataForge/pack.yml`                   | `<your-mod>`           |
| `<your-mod>/DataForge/<pack-name>/pack.yml`       | `<your-mod>/DataForge` |
| `KPatchwork/DataForge/<category>/<pack>/pack.yml` | `DataForge`            |

The linter examines every `.yml` and `.yaml` below the selected root. Choose the narrowest root that
still leaves at least one directory between the root and each `pack.yml`; otherwise unrelated YAML
files may be reported as being outside a pack.

## KPatchwork's `contributer` requirement

:::caution
The linter requires a `contributer` field spelled exactly this way. This is KPatchwork repository
ownership metadata, not a required KDataForge runtime manifest field. A standalone pack can be
valid at runtime and still fail this policy check when the field is absent.
:::

When preparing a pack for KPatchwork, add your GitHub login or a non-empty list of co-maintainers:

```yaml
ref: MyTweaks
name: My Tweaks
version: 1.0.0
contributer:
  - your-github-login
```

KPatchwork CI uses this value for ownership checks as well as linting. Changing the field in that
repository requires maintainer approval.

## What the linter checks

The current linter checks:

- YAML syntax, empty documents, and explicit `type` values in multi-document files;
- pack manifests, semver-like versions, unique refs, dependencies, missing dependencies, and
  dependency cycles;
- known document types and the filename-based `<name>.<type>.yml` convention;
- conditions, patch selectors, property paths, operation names, and required operation arguments;
- inline instances and generated IDs, including duplicate IDs within a pack;
- generated classes, unlocks, items, resources, buildings, recipes, schematics, and research-tree
  mutations;
- float/vector curve keys, modes, finite values, and duplicate key times;
- included files, image assets, data assets, localization entries, game tags, and sink-point entries;
- symlinks, YAML outside a pack, and files that escape the selected root or pack directory.

Unknown condition keys and custom document root types are warnings. Structural problems, invalid
values, missing files, and duplicate identities are errors.

## Read the result

A successful run prints the number of packs and documents it checked:

```text
lint passed: 1 pack(s), 1 YAML document(s)
```

Errors include the file and the failed rule. Fix every `error:` line, then run the same command
again:

```text
error: /path/to/pack.yml: version '1.0' is not semver-like
error: /path/to/faster-smelting.cdo.yml: cdo.patches[0] requires properties
```

The linter has no automatic-fix mode. Its only option besides help is `--root`:

```bash
uv run --locked Lint/lint_packs.py --help
```

## What static linting cannot prove

The linter parses files without loading Unreal Engine or Satisfactory. It cannot prove that an
asset or class path exists, that a reflected property has the expected runtime type, that another
mod is installed, or that two otherwise valid packs produce the intended result together.

After linting, start the game and use
[`/kdf report`](/kdataforge/getting-started#kdf-report-and-loading-changes) to check
runtime resolution and application. Use
[debug logging](/kdataforge/getting-started#debugging) when you need the before/after
value for each applied operation.
