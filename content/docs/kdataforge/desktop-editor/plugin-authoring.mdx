KDataForge has three different extension surfaces. A YAML **pack** changes game content; a
`.kdfdata` **datapack** supplies reflection data; a TypeScript **editor plugin** contributes a
typed hook to the desktop app. The npm packages below support the third surface. They do not
make arbitrary JavaScript from npm or a pack executable inside an installed editor.

## Packages and workspace setup

The editor repository contains `@kmods/kdataforge-plugin-api` for `definePlugin`, metadata,
hook, and plan types, plus `@kmods/kdataforge-plugin-builder` for the `kdf-plugin` CLI. Its
`examples/hello-plugin` and `examples/log-parser` projects are complete workspace examples.
From a checkout of the editor repository:

```sh
pnpm install --frozen-lockfile
pnpm build:plugins
pnpm --filter kdataforge-hello-plugin-example build
pnpm --filter kdataforge-log-parser-example build
```

These commands create `dist/index.js` and `dist/kdf-plugin.json` in each example. Package source
is available in the editor repository; the commands use workspace dependencies and do not
assume the packages have been published to the npm registry.

## Example: a document builder

Create a workspace package with dependencies on the API and builder packages:

```json
{
  "name": "my-kdf-plugin",
  "private": true,
  "type": "module",
  "scripts": { "build": "kdf-plugin build ." },
  "dependencies": { "@kmods/kdataforge-plugin-api": "workspace:*" },
  "devDependencies": { "@kmods/kdataforge-plugin-builder": "workspace:*" }
}
```

Put this code in `src/index.ts`:

```ts
import { definePlugin } from '@kmods/kdataforge-plugin-api';

export default definePlugin({
  id: 'hello-plugin',
  name: 'Hello Plugin',
  description: 'Previews a project note.',
  version: '1.0.0',
  capabilities: ['documentBuilder'],
  hooks: {
    documentBuilder: {
      builders: () => [
        {
          id: 'hello-note',
          title: 'Hello note',
          build: () => ({
            id: 'hello-note',
            files: [{
              path: 'hello.txt',
              content: 'Hello from a KDataForge plugin.\n',
              operation: 'create' as const,
              expectedHash: null,
            }],
            warnings: [],
          }),
        },
      ],
    },
  },
});
```

The hook returns a **plan**. A host must preview, validate, and persist its files. Use
`operation: 'create'` with `expectedHash: null` for a new file; an update needs the current
file hash. The plugin itself receives no filesystem permission from this type. The example
writes at the project root because native create transactions require an existing parent folder.

`kdf-plugin build .` typechecks the entry, bundles browser ESM, and writes a format-1 manifest
with API version, static metadata, entry name, and SHA-256 digest. It never executes plugin code
while building. `id`, `name`, `description`, `version`, `capabilities`, and optional requirements
must be literal metadata in `export default definePlugin({ ... })`; hooks can call ordinary local
TypeScript functions. Rebuilding replaces only output previously owned by the builder.

## Example: a log parser

The second workspace example declares `capabilities: ['logParser']`. Its `parse` hook receives
lines supplied by the host and returns findings with a 1-based line number, severity, raw text,
and confidence. It looks for a marker without opening or following a log file:

```ts
import { definePlugin, type LogInputLine } from '@kmods/kdataforge-plugin-api';

export default definePlugin({
  id: 'example-log-parser',
  name: 'Example Log Parser',
  description: 'Finds marked warnings in supplied KDataForge log lines.',
  version: '1.0.0',
  capabilities: ['logParser'],
  hooks: {
    logParser: {
      parse: (lines: readonly LogInputLine[]) => lines.flatMap((line, index) => {
        const raw = typeof line === 'string' ? line : line.raw;
        const marker = 'KDF EXAMPLE_WARNING:';
        const offset = raw.indexOf(marker);
        if (offset < 0) return [];
        return [{
          parserId: 'example-log-parser', raw,
          message: raw.slice(offset + marker.length).trim() || 'Marked example warning',
          logLine: index + 1, category: 'KDF', severity: 'warning' as const,
          outcome: null, confidence: 'text-match' as const,
          sourcePath: null, sourceLine: null,
        }];
      }),
    },
  },
});
```

## Make a plugin available in the desktop app

The current app registers executable plugins at build time. To ship one, add its TypeScript
descriptor to the bundled registry, add the same ID and capabilities to native descriptors,
and wire a UI surface to its hook. Guard native commands with the provider's enabled state and
project scope. Test on/off behavior, availability requirements, incomplete data, and any write
preview. The registry rejects missing hooks or undeclared capabilities; the renderer also checks
the native catalog against bundled TypeScript metadata. A built bundle by itself does not add a
plugin to **Plugins**.

The builder and API are for editor extensions. If your goal is to ship game content, start with
[Getting Started](/kdataforge/getting-started) and make a YAML pack instead.
