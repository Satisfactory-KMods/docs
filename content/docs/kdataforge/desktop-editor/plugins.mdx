Open **Settings → Plugins** to inspect installed providers and switch them on or off. Plugin
preferences belong to the local application, not to a KDataForge pack or project. Providers ship
with Pack Manager; arbitrary executable TypeScript or Rust plugins are not loaded at runtime.

Most built-ins start enabled. Specialized providers may start disabled or report limited
availability when a declared game-mod, reflected-class, datapack, or plugin requirement is
missing. **Enabled** and **available** are separate states. Switching a provider off does not
change existing YAML or project settings.

## Datapacks are resource plugins

Install a validated `.kdfdata` reflection archive from **Datapacks** or drop one file onto the
desktop window. Sources up to 2 GiB are accepted; stored reflection text is losslessly deflated
when needed so the installed archive fits the 512 MiB validation reader. Entry contents and image
bytes stay unchanged. The app stores immutable, content-addressed installed bytes and publishes
them as `datapack:<sha256>`. A verified bundled Vanilla export appears as `datapack:vanilla`; it is
the default only for projects without an explicit binding. Both kinds are disableable.

Projects store `[datapack].pluginId`. Legacy `[datapack].path` remains readable. Disabling an
explicitly bound datapack keeps that setting intact and makes validation schema-only until the
plugin is re-enabled or another archive is bound. The app never silently switches such a project
to Vanilla. Only `.kdfdata` archives are accepted as game-data packs.

New projects start explicitly in **Schema only** mode until an archive is bound after diagnostic
preview. Choose **Automatic Vanilla** in project settings to opt into the bundled fallback.

Shipping builds may report `metadataAvailable:false` even when class and property records are
present. The catalog then shows **Limited** and keeps missing engine metadata unknown. Missing
texture previews are also reported explicitly; the editor does not invent icons.

## Plugin contract

Built-in IDs and capabilities appear in both the TypeScript registry and native descriptors. The
renderer verifies that they agree before exposing hooks. A hook is a typed contribution, not a
file-system or shell permission. Native project IDs scope reads and writes; Native commands enforce
enabled state before guarded operations. Pure renderer contributions receive data supplied by the
host. Graphs, formatters, builders, and task actions return plans for preview; the host owns
validation, confirmation, and persistence.

The TypeScript contract is:

```ts
type HookCapability = keyof PluginHooks;

interface KdfPlugin {
  id: string;
  capabilities: HookCapability[];
  hooks: Partial<PluginHooks>;
  defaultEnabled?: boolean;
  requirements?: readonly PluginRequirement[];
}
```

The registry rejects a declared capability without its hook and a hook without its capability.
Datapack resources are the exception: they are native, verified files and need no renderer hook.
Plugin switches persist in the application's `plugins.json`; project YAML and Git state are not
part of that preference file.

## Adding a built-in plugin

Application contributors can extend the shipped plugin set:

1. Choose a stable ID, capabilities, default state, and optional requirements.
2. Implement and register TypeScript hooks for renderer contributions. Add the same descriptor to
   the native registry.
3. Guard every native command exposed by the provider. Keep file access project-scoped, and make
   write plans reviewable before applying them.
4. Test first-run state, enable/disable behavior, native rejection while disabled, and incomplete
   data behavior. Validate matching TypeScript and native metadata.

TypeScript support is part of application source and build. A pack cannot ship executable
TypeScript plugins to another installation.

For import workflow and conversion limits, see [ContentLib Import](/kdataforge/desktop-editor/contentlib-import).
