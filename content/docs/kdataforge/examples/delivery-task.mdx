`UKAPIDeliveryTask` is KAPI's 2D research-tree node type: a small reward/task, placed on an
integer coordinate grid, that unlocks once its neighboring parent node(s) are completed. This
feature has **no Satisfactory Plus dependency** — it only needs `KAPI` +
`KPrivateCodeLib`, so it's usable from any mod that links those two.

This page builds one complete tree end to end. For every other KAPI data asset type, see
[Adding KAPI Data Assets](/kdataforge/examples/kapi-data-assets); for the underlying YAML grammar
`mParentTask` uses, see [Value Forms](/kdataforge/reference/yaml-schema/#value-forms-by-property-type).

## Making the tree reachable

A delivery-task tree is invisible until the delivery-task **system** is unlocked. That gate is not
part of the tree: it lives on a schematic, as `UKPCLDeliveryTaskUnlock` from KPrivateCodeLib.
Without a schematic carrying it, every node below loads correctly and no player ever sees one.

The same schematic is the natural place for the two capacity unlocks, since both start at `1`: the
shared manual-delivery input inventory (`KPCLDeliveryTaskInventorySlotUnlock`) and how many tasks
can be queued at once (`KPCLDeliveryTaskQueueSlotUnlock`).

```yaml
# file: showcase-delivery-access.schematic.yml
type: schematic
conditions: { hasMod: KPrivateCodeLib }
schematics:
  - id: Schematic_DeliveryAccess
    properties:
      - path: mDisplayName
        value: Delivery Network Access
      - path: mType
        value: EST_Milestone
      - path: mTechTier
        value: 2
      - path: mCost
        value:
          - ItemClass: /Game/FactoryGame/Resource/Parts/IronPlate/Desc_IronPlate.Desc_IronPlate_C
            Amount: 50
    unlocks:
      - class: /Script/KPrivateCodeLib.KPCLDeliveryTaskUnlock # carries no properties
      - class: /Script/KPrivateCodeLib.KPCLDeliveryTaskInventorySlotUnlock
        properties:
          - path: mNumInventorySlotsToUnlock
            value: 4 # 1 base + 4 = 5 input slots
      - class: /Script/KPrivateCodeLib.KPCLDeliveryTaskQueueSlotUnlock
        properties:
          - path: mAmount
            value: 2 # 1 base + 2 = 3 tasks queued at once
```

Both slot unlocks allow repeat purchases, so putting either on a repeatable schematic adds its
amount again on every purchase. `KPCLDeliveryTaskUnlock` does not — it is a one-shot gate. See
[K-Mods Unlock Classes](/kdataforge/reference/kmods-unlock-classes#delivery-tasks-kprivatecodelib)
for the full property list.

## The grid and `mParentTask`

Each node has an `mCoordinate` (`FIntVector2` — plain `{ X, Y }`, negative values are perfectly
valid, the grid isn't anchored to the origin) and an `mParentTask` bitmask
(`EKAPIDeliveryTaskParent`: `Above` / `Left` / `Right` / `Bottom`). Each flag maps to a fixed
coordinate offset **relative to the node itself**:

| Flag    | Parent is at         |
| ------- | --------------------- |
| `Above` | `{ X, Y - 1 }`         |
| `Left`  | `{ X - 1, Y }`         |
| `Right` | `{ X + 1, Y }`         |
| `Bottom`| `{ X, Y + 1 }`         |

Every flag set on a node must point at a coordinate some other node in the tree actually occupies,
or the node is rejected at load time. Because a plain `int32` with `meta=(Bitmask, ...)` never gets
a runtime `Enum` linked to it by Unreal Header Tool, KDataForge resolves the flag names directly:
write a YAML sequence (`[Above, Left]`, recommended for multiple flags at once), a `|`-joined
string (`"Above|Left"`), or — still accepted for backward compatibility — a raw pre-computed
integer (`3`).

## Supporting assets

The tree below sets **every** applicable property on every node, including the icon, ADA message,
and Endless-only amount-multiplier curve those fields reference. Those three are generated by a
small support file, `include:`-ed so they load first (`dataasset`/`curve`/`asset` all run in the
same `Assets` stage, so ordering across document types is otherwise just file order, not implicit
— see [Document Structure](/kdataforge/reference/yaml-schema/#document-structure)):

```yaml
# file: showcase-delivery-task-support.yml
type: asset
assets:
  - id: DeliveryTaskIcon
    file: mod-logo.png # pack-relative path — any 2D image works as a placeholder
---
type: dataasset
conditions: { hasMod: KAPI }
assets:
  - id: AdaMessage_TaskComplete
    class: /Script/FactoryGame.FGMessage # UFGMessage is a UPrimaryDataAsset, so `dataasset` builds it directly
    properties:
      - path: mTitle
        value: { source: "Delivery Complete" }
      - path: mMessage
        value: { source: "Another delivery task in the showcase tree has been completed." }
---
type: curve
curveType: float
curves:
  - id: DeliveryTaskAmountMultiplier
    defaultValue: 1
    preInfinityExtrap: constant
    postInfinityExtrap: linear
    isEventCurve: false
    keys:
      - time: 0
        value: 1
        interpMode: linear
      - time: 5
        value: 2.5
        interpMode: linear
```

## A complete five-node tree

This tree deliberately starts off-origin, in negative coordinate space, to show the grid isn't
restricted to `{0,0}`-anchored positive layouts. Every node sets every `UKAPIDataAssetBase` common
field (`mName`/`mDescription`/`mIcon`/`mIsDisabled`/`mPriority`/`mTags`) and every
`UKAPIDeliveryTask` field common to both variants (`mAdaMessages`/`mToastIcon`/`mToastText`; the
two Instanced arrays, `mUnlocks` and `mTaskDependencies`, get their own sections below).
`DeliveryTask_Right` is switched to `bIsEndless: true` to demonstrate the complete Endless-only
field set (`mPoolElements`/`mTaskRewards`/`mMaxTasks`/`mAmountMultiplierCurve`/
`mAbsolutMaxItemAmount`) that a One-Time node never sets; every other node stays One-Time
(`bIsEndless: false`) and sets the complete One-Time field set (`mRewards`/`mCosts`, plus
`mSchematics` on the last node):

Five nodes, four edges: `Root` has no parent (the tree's entry point), `Above`/`Right` each depend
on `Root` alone, `AboveAndLeft` depends on **both** `Above` and `Right` at once (the multi-flag
case), and `UnlockSuperIngot` depends on `AboveAndLeft`. The two Instanced arrays, `mUnlocks` and
`mTaskDependencies`, are left unset above only to keep the tree readable — they are authorable from
a plain `dataasset` `properties:` op-list like any other instanced array, and the next two sections
add them.

## How completing a task unlocks more of the tree

A node becomes available once its `mParentTask` requirement is satisfied:

- **`bRequireAllParents: true`** (the default) — **every** flagged parent must be completed first
  (AND). `DeliveryTask_AboveAndLeft` above needs both `Above` and `Right` done.
- **`bRequireAllParents: false`** — **any one** flagged parent completing is enough (OR). Useful
  for a node reachable from more than one earlier branch, whichever the player finishes first.
- **`mTaskDependencies`** (an availability-dependency list, checked via `AreTaskDependenciesMet`)
  adds further gating on top of the parent-tree check itself — a schematic purchase, a research
  unlock, whatever the dependency subclass checks. Parent completion and `mTaskDependencies` are
  independent gates: both must pass.

For an **endless** node (`bIsEndless: true`), "unlocking more" also means more concurrent task
**slots**: `mMaxTasks` caps how many of that node's rolled tasks can be active/queued at once
(`INDEX_NONE`/`-1` for uncapped), and `mAmountMultiplierCurve` /
`mAbsolutMaxItemAmount` scale the reward amounts up as the player completes more rounds of it — so
the effective "how much can I get from this node" grows over time even though the node itself
doesn't move in the tree.

## Unlock example — force-unlocking a schematic

`DeliveryTask_UnlockSuperIngot` above is the unlock example: its `mSchematics` force-unlocks
`Schematic_PureSuperIngot` via `HandleUnlock` on completion, regardless of whether the player could
normally research or purchase it another way — the same mechanism `unlocks:` / `dependencies:` use
on schematics themselves, just triggered from a delivery-task completion instead. `mRewards`/
`mCosts` on that same node are the plain item grant/cost, independent of the schematic unlock.

## Granting unlocks from a task

`mSchematics` hands out a whole schematic. When the reward is a single capability instead, a task
carries its own `mUnlocks`: an Instanced `TArray<TObjectPtr<UFGUnlock>>` with the exact authoring
model a schematic's [`unlocks:`](/kdataforge/features/schematics#instanced-unlocks-the-normal-way-to-wire-up-a-recipe)
list uses. Because `dataasset` `properties:` builds
[instanced UObject arrays](/kdataforge/features/property-types#instanced-uobject-arrays) like any
other array, the entries are written inline — `class:` plus an optional nested `properties:`
op-list:

```yaml
# add to DeliveryTask_AboveAndLeft's properties:
- path: mUnlocks
  value:
    - class: /Game/FactoryGame/Unlocks/BP_UnlockRecipe.BP_UnlockRecipe_C
      properties:
        - path: mRecipes
          value:
            - /Game/FactoryGame/Recipes/Smelter/Recipe_IngotIron.Recipe_IngotIron_C
    - class: /Script/KPrivateCodeLib.KPCLDeliveryTaskQueueSlotUnlock # the tree paying for its own capacity
      properties:
        - path: mAmount
          value: 1
```

The lifecycle is the same one schematics use, and it matters for anything one-shot:

- **`Unlock()` runs once**, at the moment the task completes (`HandleUnlock`), alongside the ADA
  messages and `mSchematics`.
- **`Apply()` runs again** for every already-completed task on each save load (`ApplyUnlocks`).
  That is what re-asserts persistent state without re-firing item grants or toasts.

An unlock that only makes sense once — a one-time item grant — therefore belongs in `mRewards`, not
in `mUnlocks`. Anything that must survive a reload, such as a slot count or a feature gate, belongs
in `mUnlocks` precisely because `Apply()` re-runs. `GetAllUnlocks` reports a task's own `mUnlocks`
**plus** the unlocks of every schematic in `mSchematics`, which is what the task UI and tooltips
read; granting stays `HandleUnlock`'s job.

Every class on [K-Mods Unlock Classes](/kdataforge/reference/kmods-unlock-classes) and
[Base-Game Unlock Classes](/kdataforge/reference/base-game-unlock-classes) is valid here — a
delivery task is just another `FGUnlock` host.

## Gating a task on dependencies

`mTaskDependencies` is an Instanced `TArray<TObjectPtr<UFGAvailabilityDependency>>` and is written
exactly like a schematic's [`dependencies:`](/kdataforge/features/schematics#gating-a-schematic-on-prerequisites),
just as a `properties:` entry rather than a sublist:

```yaml
# add to DeliveryTask_UnlockSuperIngot's properties:
- path: mTaskDependencies
  value:
    - class: /Game/FactoryGame/AvailabilityDependencies/BP_SchematicPurchasedDependency.BP_SchematicPurchasedDependency_C
      properties:
        - path: mSchematics
          value:
            - /Game/FactoryGame/Schematics/Progression/Schematic_2-3.Schematic_2-3_C
        - path: mRequireAllSchematicsToBePurchased
          value: true
```

Parent completion and `mTaskDependencies` are **independent** gates, checked separately, and both
must pass before the node can be queued. `AreTaskDependenciesMet` also folds in the dependencies of
every schematic listed in `mSchematics` (that is what `GetAllDependencies` returns), so a task
handing out a gated schematic inherits that schematic's own prerequisites without restating them.
