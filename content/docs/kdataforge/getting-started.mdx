This tutorial creates a pack with one manifest and one patch. The patch halves the smelting time
for iron ingots. You will then confirm that KDataForge found and applied it.

You need KDataForge installed and permission to start a local game, host a game, or administer a
dedicated server. If you only want to install someone else's pack, use the
[Player guide](/kdataforge/players).

## 1. Create the pack folder

Create this folder under the mod or project that will ship the pack:

```text
<your-mod>/DataForge/
```

KDataForge searches up to six directory levels below the Unreal project directory, which is
`FactoryGame/` in a packaged game. A directory becomes a pack root when its name is `DataForge`,
uses the legacy name `data-editor`, or directly contains `pack.yml`. These names are
case-insensitive.

KDataForge ignores heavy engine directories such as `Content`, `Saved`, `Plugins`, and `Source`.
It also ignores `Docs`, `Scripts`, and directories whose names start with `.` during root discovery
and document collection. Keep pack documents outside those directories. The desktop editor and
linter use the same exclusions; direct validation of an excluded file can parse its YAML but reports
`root.ignored-directory` because the runtime will not load it.

Detected pack roots may nest. A YAML file belongs only to its deepest enclosing root, so a parent
pack does not load the same file again.

## 2. Add the manifest

Create `<your-mod>/DataForge/pack.yml`:

```yaml
ref: MyFirstPack
name: My First Pack
version: 1.0.0
```

The manifest gives the pack a stable identity. KDataForge can load a root without `pack.yml`, but
then it derives the pack ref and name from the parent directory. Moving that directory can change
the identity. Declare `ref` before release because generated content and save persistence use it.

## 3. Add the patch

Create `<your-mod>/DataForge/faster-smelting.cdo.yml`:

```yaml
type: cdo
patches:
  - target: /Game/FactoryGame/Recipes/Smelter/Recipe_IngotIron.Recipe_IngotIron_C
    properties:
      - path: mManufactoringDuration
        op: multiply
        value: 0.5
```

A `type: cdo` document edits a class default object. This patch multiplies the iron-ingot recipe's
manufacturing duration by `0.5`.

KDataForge reads every `*.yml` and `*.yaml` file below the pack root. A file may contain several
documents separated by `---`; each document then needs its own `type:`. In a single-document file,
the suffix `<name>.<type>.yml` can supply the type, but an explicit `type:` takes precedence. See
[Multiple documents per file](/kdataforge/reference/yaml-schema#multiple-documents-per-file).

Your pack now has this shape:

```text
<your-mod>/DataForge/
  pack.yml
  faster-smelting.cdo.yml
```

## 4. Load and verify the pack

1. Start the game and open a save.
2. Enter `/kdf report` in chat.
3. Find `MyFirstPack` and `faster-smelting.cdo.yml` in the report.
4. Check an iron-ingot recipe. Its smelting time should be half the original value.

`/kdf report` lists detected packs and documents, applied operations, warnings, and errors. An error
skips the affected file, document, or patch while loading continues. A warning reports a tolerated
problem, such as an unknown root type or duplicate pack ref. Info diagnostics describe expected
skips, such as a failed mod-version condition, and do not appear in `/kdf report`.

## 5. Reload an edit

After changing the YAML:

1. Save the file.
2. Run `/kdf reload` as the host or a dedicated-server administrator. You can run `KDF.Reload` in
   the host or server console instead.
3. Run `/kdf report` and check the result again.

Reload works only after initial loading has finished. It restores captured property baselines,
rescans the pack roots, and applies the current pack set in that process. It does not synchronize
connected clients.

Restart the session for frozen content registrations, irreversible world changes, and fields marked
as cold or restart-bound. Packs that generate
[native CDO helper assets](/kdataforge/features/data-assets#native-cdo-helpers-and-blueprint-requirements)
disable manual and automatic reload. Restart after changing, disabling, or removing one because its
native callbacks and caches cannot be reset live.

## Trace an applied operation

Add `debug: true` to one document to log its operations:

```yaml
type: cdo
debug: true
patches:
  - target: /Game/FactoryGame/Recipes/Smelter/Recipe_IngotIron.Recipe_IngotIron_C
    properties:
      - path: mManufactoringDuration
        op: multiply
        value: 0.5
```

You can put `debug: true` in `pack.yml` to trace every document in that pack. For all packs, run
`KDF.Debug 1`, use `/kdf debug on`, or launch the game with `-KDFDebug`. Global debug logging also
includes operations made in the in-game editor.

Each applied operation produces one line at Log verbosity:

```text
[KDF DEBUG] faster-smelting.cdo.yml: /Game/FactoryGame/Recipes/Smelter/Recipe_IngotIron.Recipe_IngotIron_C.mManufactoringDuration multiply : 2.000000 -> 1.000000
```

The line follows `<file>: <target>.<property> <op> : <before> -> <after>`. Packaged-game logs are in
`%LOCALAPPDATA%\FactoryGame\Saved\Logs\FactoryGame.log`. Search for `[KDF DEBUG]`.

You can also run `/kdf editor` to request the host-local editor window, browse live objects, edit
properties, undo or redo changes, and export those changes as YAML. The command branch does not
perform the reload/configuration host-permission check, but the editor still works only in the
process that opens it.

## Multiplayer check

Install the same pack set and versions on the host or dedicated server and every client. Each
process loads YAML independently. KDataForge does not compare checksums, reject mismatches, transfer
pack files, or stream applied operations.

Live changes made in `/kdf editor` remain in that process. Export them to YAML and distribute the
updated pack when every player needs the same values.

## If the result is missing

| Symptom | Check |
| --- | --- |
| KDataForge ignores the file | Add `type:` or rename a single-document file to `<name>.<type>.yml`. |
| One document in a `---`-separated file is ignored | Add `type:` to that document. Filename inference works only for single-document files. |
| The report says `class not found` | Use `_C` for a cooked Blueprint class, `/Script/Module.Class` for a native class, or `/KDataForge/Gen/<PackRef>.Gen_<PackRef>_<Id>` for a generated class. Generated classes do not use `_C`. An unambiguous short `id:` also works. |
| The operation is rejected | Check the operation's supported property kinds in [YAML schema](/kdataforge/reference/yaml-schema#operations) and [Operations](/kdataforge/features/operations). |
| A data-asset instance is not found | Remove `_C`; object instances are not classes. See [Targeting](/kdataforge/features/targeting). |
| A changed default does not affect placed buildings | A save or archetype can override the default. Use `applyToSpawnedActors` where appropriate; see [Buildings](/kdataforge/features/buildings). |

For a longer diagnosis, follow
[Debug a pack that will not apply](/kdataforge/tutorials/debugging-a-pack-that-wont-apply).
