YAML pack authors do not need the module details on this page. KDataForge discovers their pack
files through the runtime loader. This information is for contributors to
KDataForge's C++ runtime and built-in handlers, and for third-party mod authors registering a
**native handler** for a document root type. It explains where code belongs, which dependencies it
may use, and which interfaces are stable across releases.

KDataForge is one Unreal plugin with five runtime modules and one Unreal Editor module. Each
boundary isolates a public contract, parser dependency, reflection export workload, runtime UI, or
editor commandlet.

## Why the split exists

Five concerns drive where a module boundary sits:

- **Contract isolation.** Third-party mods that want to add a handler must link against something
  stable. Bundling that contract into the same module as the fast-moving loader/reflection internals
  would mean every internal refactor risks an ABI break for downstream mods. `KDataForgeApi` exists
  so that contract can stay frozen while everything else evolves underneath it. See
  [API Design](/kdataforge/reference/api-design) for what that contract
  contains.
- **Exception containment.** The vendored YAML parser (rapidyaml) reports errors by throwing, but
  the rest of the codebase doesn't build with C++ exceptions enabled. Rather than flip on exceptions
  plugin-wide, only the module that wraps the parser does.
- **UI dependency isolation.** The in-game editor pulls in `InputCore`, `UMG`, `Slate`,
  `SlateCore`, and `AppFramework`. Keeping it in `KDataForgeEditorUI` stops those dependencies from
  leaking into the loader/reflection runtime, even though the module itself is still declared as a
  Runtime module.
- **Reflection export isolation.** Runtime and commandlet reflection exports scan large type and
  asset catalogs and can read texture data. `KDataForgeReflection` keeps that toolchain separate
  from normal pack loading.
- **Localization commandlet isolation.** YAML text gathering needs Unreal Editor localization
  modules. `KDataForgeLocalization` is an Editor module, so those dependencies never enter game or
  dedicated-server targets.

## The six modules

Five modules are declared `"Type": "Runtime"` in the `.uplugin` manifest: `KDataForgeApi`,
`KDataForgeYaml`, `KDataForge`, `KDataForgeReflection`, and `KDataForgeEditorUI`.
`KDataForgeLocalization` is declared `"Type": "Editor"`. The runtime also links the external
`KDFFlacLibrary` module under `Source/ThirdParty`; it is a library wrapper, not one of the plugin
modules listed in the manifest.

That's a deliberate naming trap worth calling out. "EditorUI" refers to an **in-game** editor
window rendered with hand-built Slate while the game is running, not to Unreal Editor-only code.
Nothing in that module is gated behind `WITH_EDITOR`, and none of its dependencies are editor-only
modules. It has to build and link cleanly anywhere the plugin loads it.

### `KDataForgeApi` the public contract

Third-party mods use this module for handler types and keep it intentionally tiny:

```
Source/KDataForgeApi/Public/
├── KDFDataEditorHandler.h
├── KDFHandlerBase.h
├── KDFNode.h
├── KDFConfigTypes.h
├── KDFTemplateProvider.h
└── KDFTypes.h
```

Its dependency list is just `Core`, `CoreUObject`, and `Engine`, nothing else. That's not an
accident of an early prototype. It's rule #2 below: adding a dependency here is treated as an
API-breaking decision, because every third-party handler mod inherits whatever this module pulls
in. The types used here (`FKDFNode`, `UKDFHandlerBase`,
`IKDFDataEditorHandler`) are covered in [API design](/kdataforge/reference/api-design).
A worked handler implementation against this exact module lives on the
[Handler Template](/kdataforge/reference/handler-template) page.
The native template-provider contract has its own
[reference](/kdataforge/reference/template-provider-api).

### `KDataForgeYaml` the YAML backend

This module exists for one reason: to keep exceptions from leaking anywhere else in the plugin.
`KDFYamlParser.h` parses a document that throws `ryml::Callbacks::error` and turns it into a clean
`FKDFNode` tree or an error string, entirely inside this module:

```
Source/KDataForgeYaml/
├── Public/   KDFYamlParser.h              (façade the only entry point)
├── Private/  KDFYamlParser.cpp            (ryml + a deterministic hand-written emitter)
└── ThirdParty/ryml/rapidyaml.hpp          (v0.15.2 amalgamation vendored, never edited)
```

`bEnableExceptions = true` is set only in this module's `.Build.cs`. The reasoning is spelled out
right next to it: rapidyaml reports parse errors through a callback that throws, and that has to
stay contained to this wrapper. The public surface only ever returns `FKDFNode` trees and error
strings, never a ryml type or an exception across a module boundary. Its own dependencies are
`Core`, `CoreUObject`, and `KDataForgeApi` (for `FKDFNode`). Nothing pulls FactoryGame or SML in
here.

### `KDataForge` the main runtime

This is where nearly everything lives: the loader, the reflection engine, the built-in handlers,
the subsystems, and the pieces that don't get their own module because they're not a public
contract, an exception boundary, or an editor-only concern. Layering inside it happens at the
folder level, not via further module splits:

```
Source/KDataForge/{Public,Private}/
├── Reflection/       KDFPropertyPath · KDFValueCodec · KDFOpEngine · KDFVanillaCache · KDFPatchUtil
├── Loader/           KDFPackScanner · KDFConditionEvaluator · KDFLoaderTypes
├── Content/           KDFDynamicContent (class/asset generation, manifest, tombstones) ·
│                       KDFRecipeRemoval · KDFSoundLoader · KDFSoundEvent · KDFSoundPreview
├── Config/            descriptions and widgets contract · registry · persistence · reload scheduler ·
│                       console commands · sound options integration
├── Template/          built-in providers · expansion · configuration expressions · cold-property catalog
├── Subsystems/        KDFSubsystem · KDFActorPatchSubsystem · KDFStateSubsystem ·
│                       KDFContentRemoveSubsystem · KDFResourceNodeSubsystem · KDFEventRuleSubsystem
├── Handlers/          KDFCdoHandler · KDFAssetHandler · KDFCurveHandler · KDFGameTagHandler ·
│                       KDFContentClassHandler family (Class/Item/Resource/Building/Recipe/
│                       Schematic/Research/Unlock) · KDFDataAssetHandler ·
│                       KDFSinkPointsHandler · KDFLocalizationHandler · KDFSublevelHandler ·
│                       KDFResourceNodeHandler · KDFSoundHandler · KDFCategoryReorderHandler ·
│                       KDFEventRuleHandler
├── Commands/           KDFChatCommand
├── Module/             KDFGameInstanceModule · KDFWorldModule (SML root modules)
├── Net/                 KDFRemoteCallObject (host-gated RPC scaffold)
└── EditorIntegration/   KDFEditorApply (WITH_EDITOR-gated, private-only: `KDF.ApplyToAssets`
                         console command bakes cdo documents directly onto UE-editor assets)
```

`EditorIntegration/` is the one genuinely editor-only corner of the whole plugin, and it earns that
by being gated behind `WITH_EDITOR` at the file level rather than by living in its own module. It
never ships to Shipping or dedicated-server builds, and it has no public header at all, since
nothing outside this one `.cpp` needs to call into it.

`Net/` contains a host-gated `Server_ApplySetOp` RPC scaffold. The current editor does not call it,
and there is no checksum handshake or operation stream. See the current multiplayer boundaries in
[Architecture](/kdataforge/background/architecture#multiplayer-boundaries).

Its dependency list is the longest of the runtime core: `Core`, `CoreUObject`, `Engine`, `Projects`,
`Json`, `GameplayTags`, `NetCore`, `AssetRegistry`, `ImageWrapper`, `RenderCore`, `RHI`, the
`DummyHeaders` stub module, `FactoryGame`, and `SML`, plus `KDataForgeApi` and `KDataForgeYaml`.
Sound loading also links `KDFFlacLibrary`, `VorbisAudioDecoder`, Wwise modules, and Unreal's Ogg,
Vorbis, and VorbisFile libraries. `ImageWrapper`, `RenderCore`, and `RHI` back `type: asset`
documents, turning supported 2D image files into runtime `UTexture2D` assets through
`KDFAssetHandler`.

### `KDataForgeEditorUI` the in-game editor

Kept as its own module so Slate, UMG, and AppFramework stay isolated from the main runtime module:

```
Source/KDataForgeEditorUI/
├── Public/   KDFEditorSubsystem.h · KDFEditorModel.h
└── Private/  SKDFEditorWindow.* · KDFEditorStyle.h    (pure code-built Slate, no UMG assets)
```

The editor window needs to read the loader's pack manifests, walk `FKDFNode` trees, and apply ops
through the same reflection engine the runtime uses to build its Diff and Apply tabs. Because of
that, it depends on all three other modules: `KDataForgeApi`, `KDataForgeYaml`, and `KDataForge`,
alongside `InputCore`, `UMG`, `Slate`, `SlateCore`, `AppFramework` (for `SColorPicker`),
`AssetRegistry`, `FactoryGame`, and `SML`. The wiring between this window and the runtime it edits
is covered on [Editor Integration](/kdataforge/reference/editor-integration).

### `KDataForgeReflection` the export toolchain

This runtime module owns reflection export, texture previews, the `/kdf-reflection` and
`/kdf-export` chat commands, `KDF.DumpReflection`, validation, and the metadata export commandlet.
It depends publicly on the engine, Projects, JSON, Asset Registry, FactoryGame, SML, and
`DummyHeaders`. Its private dependencies include `KDataForge`, `ImageCore`, `RenderCore`, and `RHI`.

Keeping the exporter separate lets ordinary pack loading avoid its scanning and image-export code.
The output contract and recovery workflow are documented in
[Reflection export](/kdataforge/reference/reflection-export).

### `KDataForgeLocalization` the editor commandlet

This Editor module contains `GatherKDataForgeTextCommandlet`. It reads pack YAML during Unreal's
localization workflow and depends on `UnrealEd` and `Localization` alongside the YAML and API
modules. It never loads in packaged game or dedicated-server targets.

The two localization paths and their source-key rules are documented in
[Localization](/kdataforge/features/localization).

## Dependency graph

Arrows below point from a module to what it depends on. `KDataForgeApi` has the smallest runtime
footprint. Reflection and localization tooling sit beside the main runtime instead of adding their
dependencies to every pack load:

```
KDataForgeEditorUI   → KDataForge, KDataForgeYaml, KDataForgeApi
                        (+ InputCore, UMG, Slate, SlateCore, AppFramework, AssetRegistry,
                           FactoryGame, SML)
        ▲
KDataForge           → KDataForgeYaml, KDataForgeApi
                        (+ Engine, Projects, Json, GameplayTags, NetCore, AssetRegistry,
                           ImageWrapper, RenderCore, RHI, DummyHeaders, FactoryGame, SML)
        ▲
KDataForgeYaml       → KDataForgeApi                              [bEnableExceptions]
                        (+ Core, CoreUObject)
        ▲
KDataForgeApi                                                     (Core, CoreUObject, Engine only)

KDataForgeReflection → KDataForge
                        (+ Projects, Json, AssetRegistry, ImageCore, RenderCore, RHI,
                           DummyHeaders, FactoryGame, SML)

KDataForgeLocalization [Editor] → KDataForgeYaml, KDataForgeApi
                                  (+ Projects, UnrealEd, Localization)
```

> Link-dependency lesson (Shipping builds): the dev-editor target resolves symbols that the modular
> Shipping DLLs do not. `EKeys` needs **InputCore**, `UModContentRegistry` needs **SML**, and
> `FKDFYamlParser` needs **KDataForgeYaml**. A Shipping package run is the real link check, not a
> dev-editor compile.

## Rules for contributors

These aren't style preferences. Each one closes off a class of bug that's already bitten this
plugin once:

1. **ryml types never cross the `KDataForgeYaml` boundary.** The façade returns `FKDFNode` trees and
   error strings only. Exceptions exist only inside that module, per `bEnableExceptions` above.
2. **`KDataForgeApi` stays tiny and dependency-free** (`Core`, `CoreUObject`, `Engine`). Adding a
   dependency there is an API-breaking decision for every third-party handler mod. Treat it as such.
3. **No editor-only module dependencies anywhere.** The plugin must build for Shipping and
   dedicated servers. Editor-only code, if ever needed, goes behind `Target.bBuildEditor` in
   `.Build.cs` plus `WITH_EDITOR` guards (see `EditorIntegration/` above for the one place this
   already applies).
4. **Handlers live in the main module** or in third-party mods. Third-party handler types derive
   against `KDataForgeApi`; calling `UKDFSubsystem::RegisterHandler` also requires `KDataForge`.
   Handlers never include loader or scanner internals. Everything they need arrives via the context structs that the
   [Handler Template](/kdataforge/reference/handler-template) walks through.
5. **All six plugin modules share the same build settings:** `CppStandard = Cpp20`,
   `PCHUsage = UseExplicitOrSharedPCHs`, `bLegacyPublicIncludePaths = false`, and the project's clang-format
   is enforced across all of them.

For how these modules cooperate at runtime, the fixed stage pipeline, the reflection engine, and
savegame persistence, see [Architecture](/kdataforge/background/architecture).
