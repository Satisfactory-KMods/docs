This section explains why KDataForge behaves as it does and how its runtime modules work together.
Pack authors do not need it for routine YAML work. Read it when you are designing around load order,
save identity, reload limits, or multiplayer, or when you are adding a native handler.

- [Architecture](/kdataforge/background/architecture) follows a document from filesystem discovery
  through YAML parsing, fixed-stage application, reflection-based property edits, generated-content
  persistence, reload, and the current multiplayer boundary.
- [Module structure](/kdataforge/background/module-structure) maps the runtime modules, their source
  layout, and their dependency rules. Those boundaries keep public integration contracts separate
  from parsing, reflection export, runtime application, and user-interface code.

Use [API design](/kdataforge/reference/api-design) for the supported native integration surface and
the [handler template](/kdataforge/reference/handler-template) when implementing a document type.
